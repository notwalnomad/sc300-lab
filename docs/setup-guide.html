What you're building

A small pretend company inside your own Microsoft tenant: a couple of admin accounts, a few users and groups, a guest, some apps and some security policies. Then you prove each change happened by finding it in the logs.

Three websites

  • Azure portal (portal.azure.com): money and machines. Subscriptions, resource groups, budgets, VMs.
  • Entra admin center (entra.microsoft.com): identity. Users, roles, MFA, Conditional Access, apps, logs.
  • Microsoft 365 admin center (admin.microsoft.com): licenses and trials.

Type these addresses yourself rather than clicking links in emails.

Browser habits

  • One browser profile per account (your admin, Lab-Admin, Lab-Helpdesk, lab.user1). Private windows work too.
  • Test sign-ins and MFA in a fresh private window, or you'll see results from an old session.

How each day works

  1. Read the day's goal.
  2. Do each step in your tenant, check You should see, then tick it.
  3. Answer the Check yourself questions before peeking.
  4. Work the matching records in the Lab Inbox simulator.
Why this course keeps saying "prove it": in a real job, "I set it up" isn't enough. Auditors and incident responders want evidence: an audit event, a sign-in record, a request ID. Each step below says where that evidence lives.

Day 0: Azure and Entra setup

Goal: find your tenant, create two lab accounts, give one a role and the other a license, and put a spending safety net in place. No VMs today.
Day 0 finish line: you can point to your primary domain, both lab users, Lab-Admin's role, Helpdesk's P2 license, an empty rg-sc300-lab, and the budget.
Check yourself
Helpdesk has an Entra ID P2 license. Can it reset passwords yet?
No. A license unlocks features but grants no permissions. Resetting passwords needs a role (Helpdesk Administrator), which comes on Day 1.
You created an empty resource group. Are you being charged?
No. Resource groups are free containers. Charges start when you create billable resources inside them, such as VMs.
Your budget alert at 100% fires. Does Azure stop the spending?
No. Budgets only send alerts. You have to stop (deallocate) or delete the resources yourself.

Day 1: Users, groups, roles and hybrid identity

Goal: understand who an identity is, what access it has, and where it comes from.
The big idea: role = what an admin can do. Scope = where they can do it. Most admin mistakes are the right role at the wrong scope.

Check yourself
Helpdesk tries to reset SC300-Lab-Admin's password and fails. Is something broken?
No, the scope is working. Helpdesk Administrator is scoped to AU-Lab, and SC300-Lab-Admin isn't in it. A failed attempt outside the fence is your proof that the fence works.
Does owning a group make you a tenant admin?
No. Owners manage the group's membership. Admin rights come from roles, and only a role-assignable group passes roles on to its members.
Why is "synced user exists" not enough to pass the hybrid lab?
User sync, group sync, domain join, hybrid device registration and PRT state are separate systems. Each can fail on its own, so each needs its own check.

Day 2: MFA, Conditional Access and sign-in logs

Goal: prove MFA happened using the sign-in logs, and test a Conditional Access policy without enforcing it.
The big idea: "it prompted for MFA" and "this policy required MFA" are two different claims. Each one needs its own evidence.

Don't switch the policy On, turn off security defaults, reset passwords or add permissions just to make a sign-in look like a screenshot.
Check yourself
Point to proof that MFA happened in a specific sign-in. Where is it?
Sign-in logs → that event → Authentication details. A row showing an MFA method succeeding in that event, not "previously satisfied".
The Report-only tab says "Failure". Was the user blocked?
No. Report-only never blocks. "Failure" means the user would have failed the grant controls if the policy were On. Check the top-level status for what really happened.
Why exclude an emergency access account from Conditional Access?
So a broken policy can never lock every admin out. The emergency account is the way back in.

Day 3: SAML SSO, app registrations and Microsoft Graph

Goal: connect an app to your tenant, then show what a delegated token can and can't do.
The big idea: getting a token proves who you are. It doesn't decide what you're allowed to do. Permissions and assignments do that.

Lab 1: SAML single sign-on

Lab 2: App registrations

Lab 3: Microsoft Graph

Graph Explorer can show GET /me quickly, but it signs in as its own app, so it can't test your app's permissions. The script is the real test.
Check yourself
Explain the difference between a person, an app registration, a service principal, a SAML assertion and a delegated access token.
Person: the user account that signs in. App registration: the app's definition (ID, permissions it asks for). Service principal: that app's identity inside your tenant, where consent and assignments live. SAML assertion: a signed message telling an app who the user is (used for SSO). Delegated access token: lets an app call an API on behalf of the signed-in user, limited to both the user's rights and the consented permissions.
A developer says "the 403 is blocking me, grant User.Read.All". What do you say?
Not yet. The 403 shows the permission boundary is working. Ask what business need requires listing users, then consider the least privilege that meets it (for example User.ReadBasic.All) through the normal consent review.
A user gets AADSTS50105. Should you reset their password?
No. The password was accepted. The user simply isn't assigned to the app. Assign them only if they should have access.

Day 4: PIM, access reviews and entitlement management

Goal: control how privileged access is granted, and make sure access is removed when it's no longer needed. Needs Entra ID P2.

The course emails you shared cover Days 0–3 and say Day 4 is PIM, access reviews and access packages. These steps come from the Lab Inbox's Day 4 tickets.

Check yourself
Jamie's eligible role activation arrives at 2 a.m. with the reason "fix". Approve?
No. Deny it, contact Jamie through a channel you already trust, and check the account's sign-ins. Off-hours timing plus a vague reason is exactly what approval exists to catch.
What's the difference between active and eligible?
Active: the rights are always on. Eligible: no rights until the user activates the role for a limited time, usually with MFA, a reason and maybe approval.
Your access review denied the guest. Is the guest account deleted?
Not by default. The review removes the access it covered (here, group membership). Guest reviews can also be configured to block and later remove denied guests.

Where to find evidence

Every change leaves a trail. Here's where to look, and what to search for.

Which log?

  • Directory changes (users, groups, roles, apps, policies): Entra → Monitoring & health → Audit logs. Open an event → Modified properties shows old and new values.
  • Sign-ins: Sign-in logs → Basic info, Authentication details, Report-only tab.
  • Azure resources (resource groups, VMs, budgets): the resource → Activity log. Separate from Entra's logs.
  • PIM: PIM → Microsoft Entra roles → Resource audit.

Audit activities to filter on

  • Add user · Update user · Change user license
  • Add member to role · Add scoped member to role
  • Add member to group · Remove member from group
  • Revoke sessions: Update StsRefreshTokenValidFrom Timestamp
  • Admin reset: Reset password (by admin)
  • Invite external user · Redeem external user invite
  • User registered security info
  • Add conditional access policy
  • Consent to application · Add delegated permission grant

Microsoft renames activities from time to time. If a filter finds nothing, filter by the target instead.

Emailed or only logged?

A real tenant can email you about PIM changes, budget alerts, guest invites, admin consent requests, access reviews, access packages, SAML certificate expiry and Cloud Sync quarantine. Most need setting up first.

Everything else is only in the logs. That's why you learn to read them.

Glossary

Plain-English definitions for the terms in this guide.

Tenant
Your organization's identity directory in Entra: users, groups, apps, settings. Identified by its primary domain and Tenant ID.
Subscription
Where Azure charges are billed. Resources live inside it.
Resource group
A named folder for Azure resources. Empty ones cost nothing.
License
Unlocks features for a user. Never grants admin permissions.
Role
A set of admin permissions, such as resetting passwords or managing apps.
Scope
Where a role applies: the whole directory, or one administrative unit.
Administrative unit
A container that limits what a scoped admin can manage.
Guest (B2B)
An outside user who signs in with their own account. User type = Guest.
Cloud Sync
Copies users and groups from on-prem Active Directory into Entra.
Hybrid joined device
A Windows PC joined to on-prem AD and also registered in Entra.
PRT
Primary Refresh Token: a joined device's long-lived token for single sign-on.
MFA
Multifactor authentication: something you know plus something you have or are.
Number matching
You type the number from the sign-in screen into Authenticator, so you can't blindly approve a prompt you didn't start.
Previously satisfied
No new MFA prompt. The session already had an MFA claim.
Conditional Access
If-then rules for sign-ins: if this user, app or risk, then require MFA, block, and so on.
Report-only
A Conditional Access policy that records its result but never enforces it.
Security defaults
Microsoft's basic tenant-wide protection, including MFA. Replaced by Conditional Access in larger setups.
Emergency access account
A "break-glass" Global Admin excluded from Conditional Access, used only if everyone else is locked out.
Temporary Access Pass
A short-lived, often one-time passcode an admin issues so a verified user can sign in and re-register MFA.
SSO
Single sign-on: sign in once to Entra, and Entra vouches for you to apps.
SAML assertion
A signed message telling an app who the user is. NameID is the user identifier inside it.
App registration
An app's definition: its ID and the permissions it asks for.
Service principal
An app's identity inside your tenant (under Enterprise applications).
Delegated permission
Lets an app act on behalf of the signed-in user, limited by what that user can do.
Admin consent
An admin approving an app's permissions for everyone in the tenant. Treat it carefully.
Device code flow
Sign-in where an app shows a code that you enter on a browser page.
PIM
Privileged Identity Management: just-in-time, time-limited, approved admin roles.
Eligible vs active
Eligible: activate when needed. Active: always on.
Access review
A periodic check that people still need their access.
Access package
Requestable bundle of access with approval and an expiry date.
Lifecycle workflow
Automated joiner/mover/leaver tasks. Needs ID Governance.
Deallocated
A stopped VM that isn't billed for compute. "Stopped" from inside Windows is not enough.

Cleanup and ground rules

Keep costs at zero

  • After every hybrid session: each VM → Stop → Stopped (deallocated).
  • Budget alerts warn, they never stop charges.
  • When the course is done, delete rg-sc300-lab (everything inside goes with it), the guest and the test users.
  • Check the Microsoft 365 admin center → Billing for trials that convert to paid.

Always

  • Work in a lab tenant you own.
  • Keep an emergency access account excluded from Conditional Access.
  • Find the evidence before moving on.
  • Hide passwords, tenant IDs and personal details in screenshots you share.

Never

  • Share passwords or MFA codes with anyone, including an instructor or an AI assistant.
  • Disable security controls or add permissions to match a screenshot.
  • Give the helpdesk account a tenant-wide admin role.
  • Build paid resources before the budget exists.
